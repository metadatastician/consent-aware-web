= Proof Requirements — consent-aware-web
:toc: preamble

== Proof Tier

*Tier*: T5 — Exempt

[IMPORTANT]
====
This file previously declared *T3 — Standard* with seven obligations: five ABI/FFI
and two typing. Those were inherited from the RSR template and referred to
`src/interface/Abi/` (Idris2) and `src/interface/ffi/` (Zig) — a C ABI seam this
project never had. Both trees were removed at extraction as capability fiction, so
the obligations they generated no longer exist.

Declaring proof obligations against absent code is the same failure as declaring
capabilities you do not have: it makes the oracle score empty modules.
====

== Why T5

There is no code whose correctness a machine-checked proof would establish.

* The deliverables are two documents and a JSON Schema.
* The reference implementation is illustrative, not normative. If it disagrees with
  the drafts, the drafts win — so proving the implementation correct would prove
  the wrong artefact.
* There is no ABI, no FFI seam, no concurrency, no cryptography. AIBDP deliberately
  carries no crypto; that is recorded in `docs/status/SCOPE.adoc` as the boundary
  against AVOW.

Verification that *does* apply here is empirical and lives in `spec-gates.yml`:
structural validation of the drafts, schema validation of every manifest, and
assertion of enforcement behaviour over real HTTP requests.

== What would warrant proofs later

Recorded so the T5 is a considered position rather than an absence of thought.

[cols="1,3,2",options="header"]
|===
| Code | Obligation | Trigger

| DOM
| *Policy resolution is deterministic and total.* Given a manifest, a purpose and a
  path, `policies[purpose]` → `scope` → `exceptions` must yield exactly one outcome,
  independent of key order, and must be defined for every input. Today this order is
  specified only in code and prose, not normatively in the draft.
| A second implementation, or a conformance suite. Two implementations disagreeing
  about exception precedence is the first real interoperability failure this
  protocol can have.

| INV
| *Exceptions narrow, never widen.* An `exceptions` entry should not be able to grant
  a permission the enclosing policy refuses — otherwise a manifest can be written
  whose plain reading and machine reading differ.
| Before `-01`. This is a specification question, not an implementation one, and it
  is currently unanswered.

| ALG
| *Path-pattern matching terminates and matches what a reader expects.* `pathMatches`
  compiles glob-ish patterns to regular expressions; `/docs/**` and `?` semantics are
  neither specified nor unit-tested.
| Alongside the conformance suite.

| SEC
| Not applicable unless the optional COSE/JWS manifest signature described in
  `draft-jewell-aibdp-00` is implemented. It is not.
| Implementation of manifest signing.
|===

None of the above is scheduled. `INV` is the one that should be resolved as
*specification text* before submission, whether or not it is ever proven.

== Proof categories

[cols="1,3,1",options="header"]
|===
| Code | Meaning | Applies?

| *TP* | Typing Proofs (type soundness, type safety) | No — no typed seam
| *INV* | Invariant Proofs (state machines, monotonicity, bounds) | Deferred — see above
| *SEC* | Security Proofs (crypto, injection freedom, access control) | No — no crypto
| *CONC* | Concurrency Proofs (linearizability, deadlock freedom) | No — no concurrency
| *ALG* | Algorithm Proofs (termination, correctness, bounds) | Deferred — see above
| *DOM* | Domain Proofs (protocol semantics) | Deferred — see above
| *ABI* | ABI/FFI Proofs | No — removed at extraction; there is no ABI
|===
