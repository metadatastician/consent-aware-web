IETF-track specifications for consent-aware HTTP: AIBDP manifests and the 430 Consent Required status code

== Overview

Consent-Aware Web is a specification suite for ethical AI governance on the web:
a way for content originators to declare what AI systems may and may not do with
their content, and for origins to enforce those declarations at the HTTP layer.

It began as a `robots.txt`-shaped idea and grew into a consent model — because
`robots.txt` governs *crawling*, and the question that matters now is *use*.

== Problem

The web has no standard way to express, or enforce, any of the following:

* machine-readable AI usage boundaries
* transparent identification of AI agents
* enforceable consent
* verifiable content provenance
* standardised compliance reporting

== Architecture — and what is actually specified

The full framing is six layers. *Two are specified today.* The remaining four are
intended, not drafted, and are listed here as direction rather than deliverable.

[cols="1,2,3,1",options="header"]
|===
| Layer | Protocol | Purpose | Status

| Declaration
| AI Boundary Declaration Protocol (AIBDP)
| Declares permitted and prohibited AI uses of content
| *`draft-jewell-aibdp-00`*

| Enforcement
| HTTP Status Code 430 (Consent Required)
| Runtime enforcement of consent requirements
| *`draft-jewell-http-430-consent-required-00`*

| Identity
| AI Agent Identification Protocol
| AI systems declare who they are and what they do
| not drafted

| Consent Flow
| Web Consent Management Protocol
| How consent is requested, granted and tokenised
| not drafted

| Provenance
| Content Provenance Protocol
| Origin and AI involvement in content
| not drafted

| Accountability
| AI Compliance Reporting Framework
| Monitoring, audit and violation reporting
| not drafted
|===

Both drafts are `-00` and have *not* been submitted to the IETF datatracker. See
`.machine_readable/descriptiles/STATE.a2ml` for the current position and blockers.

== How it works

An origin publishes a manifest at `/.well-known/aibdp.json` declaring its
policies. When a request arrives whose declared or inferred AI purpose violates
one of those policies, the origin answers *430 Consent Required* rather than 200
or 403 — a distinct code, because the refusal is procedural (consent was never
established) rather than authorisation (403) or legal (451).

This repository publishes its own manifest at `.well-known/aibdp.json`. That is
not decoration: the `dogfood-gate` and `schema-validate` jobs fail if it is
missing or invalid.

== Quick start

[source,bash]
----
just test                   # validate drafts, manifests, links, expiry
just build-drafts           # render drafts/*.xml

cd examples/reference-implementations/bun && bun run example_server.js
curl -o /dev/null -w '%{http_code}\n' localhost:5000/article -H 'User-Agent: GPTBot/1.0'   # 430
----

== What you get

* *Machine-readable metadata* (`.machine_readable/descriptiles/`) — `STATE`, `META`,
  `ECOSYSTEM`, `PLAYBOOK`, `AGENTIC`, `NEUROSYM`, `CLADE`, and `anchors/ANCHOR`,
  in a2ml, so tools and agents can read the project's state and boundaries.
* *AI gatekeeper protocol* — `0-AI-MANIFEST.a2ml` is the universal entry point that
  tells an AI agent how to work in this repo before it touches anything.
* *Typed ABI/FFI seam* — `src/interface/Abi/` (Idris2 type + layout proofs) over
  `src/interface/ffi/` (Zig implementation), with generated C headers.
* *CI/CD* — GitHub Actions for quality, security (CodeQL, Scorecard, secret
  scanning), multi-forge mirroring, and RSR anti-pattern enforcement.
* *Supply-chain & reproducibility* — container layering (stapeln), Guix shells,
  SBOM, and signing hooks.
* *Governance* — `GOVERNANCE.adoc`, `MAINTAINERS.adoc`, `.github/` community health
  files, and a release `AUDIT.adoc` gate.
